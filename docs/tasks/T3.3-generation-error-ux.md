# T3.3 — Generation error UX

- **Milestone:** M3 Real generation
- **Status:** done
- **Depends on:** T3.2 (done: the `llm_*` codes exist), T1.4 (Page 1)
- **Plan sections:** 4.4 (error codes), 4.8 (Page 1), 6 (T3.3), 7 (frontend tests)

## Goal

When ticket generation fails, Page 1 shows a plain-language message for the error code, with a Retry button where retrying can help. The transcript in the box is never changed or lost.

## Files

Create or change only these. Anything else: ask first.

- `web/src/errorMessages.ts` (new, pure: `describeGenerationError(error)` returns `{ message, retryable }`)
- `web/src/errorMessages.test.ts` (new: Vitest for the mapping)
- `web/src/report/ReportPage.tsx` (use the mapping; Retry button)
- `web/src/report/ReportPage.test.tsx` (error display, Retry, transcript kept)
- `web/src/styles.css` (only if the Retry button needs a style)
- `docs/tasks/T3.3-generation-error-ux.md` and `docs/status.md` (log and state)

## Out of scope

- API changes: no new codes, no change to ProblemDetails (`api.ts` already passes `code` through as `ApiError.code`).
- Messages for transcription errors (the recorder keeps its own; error review is T6.1).
- Automatic retry, backoff, or a countdown. Retry is a user click.
- Showing raw server text such as `detail` for `llm_*` codes (it may name the provider or contain internals).
- Page 2 (T4.x), and any change to the prompt, contract or validator.

## Acceptance criteria

- [ ] `describeGenerationError` returns a distinct, human-readable message for each of `llm_refused`, `llm_invalid_output`, `llm_truncated`, `llm_unavailable`, `llm_timeout`, and for the client codes `network_error` and `unexpected_response`.
- [ ] Unknown codes and non-`ApiError` values fall back to a generic message; `validation` keeps the server's message (it names the length rule).
- [ ] Each message says what happened and what to do next, without code names, HTTP status numbers or provider internals.
- [ ] A `retryable` flag decides whether the Retry button is shown (see Questions).
- [ ] Clicking Retry sends the transcript currently in the box (not a stale copy) and clears the error while running.
- [ ] After any error the textarea still holds the same text, including text edited after the error appeared.
- [ ] The error is announced (`role="alert"`) and the Generate button stays usable.
- [ ] A successful retry moves to Page 2 as before.
- [ ] Vitest covers the mapping table and the Page 1 behaviour above; `npm test`, `npm run lint` and `npm run build` pass.

## Notes

- Code to message mapping and the `llm_*` HTTP statuses: status.md decision log (T3.2): `llm_refused` 422, `llm_invalid_output` 502, `llm_truncated` 502, `llm_unavailable` 503 (also bad key), `llm_timeout` 504.
- `App.tsx` already owns the transcript, so it survives errors; the task only has to avoid clearing it.
- The invalid-key case maps to `llm_unavailable` by design (T3.2), so the message must not claim "bad key" with certainty.

## Questions for the human (answer before work starts)

1. **Retry for `llm_refused`:** the model declined the content, so an identical retry will likely fail. Proposal: no Retry button; message says to edit the transcript and press Generate. Retry shown for all other `llm_*` codes, `network_error` and `unexpected_response`. OK?
2. **Retry for `llm_invalid_output` and `llm_truncated`:** a second try may succeed (D15 says the user regenerates, no automatic retry), and `llm_truncated` suggests shortening the report. Proposal: Retry shown for both, truncated message also suggests a shorter transcript. OK?
3. **Button label/placement:** Retry replaces nothing; it sits next to the message, and Generate ticket stays as is (both do the same call). Acceptable, or should Generate be hidden while an error shows?
