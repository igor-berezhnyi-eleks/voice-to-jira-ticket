## Goal

Page 2 lets the developer edit every field of the generated ticket (strings and lists), see which fields hold no real content ("Not provided" or an empty list), and jump from a missing-information question to its field. The edit lives in the browser only; nothing is sent to the API.

## Acceptance criteria

- [ ] Every field is editable: title and description; for a Bug steps to reproduce (list), actual result, expected result, environment; for a Feature user or business need, proposed behavior, acceptance criteria (list). Only the fields of the ticket's type appear.
- [ ] Single-line strings (title) use an input, the rest a textarea; every control has an accessible label (the existing field labels).
- [ ] List fields show one row per item with Add, Remove, Move up and Move down; Move up is disabled on the first row, Move down on the last; the pure functions return new arrays and leave the input unchanged.
- [ ] `isNotProvided` is true for exactly `"Not provided"` and for an empty list, false for any other text (including `"Not provided."` and different case) and for a list with at least one item. (Blank text and blank list items: see Questions 1 and 2.)
- [ ] A field that is not provided is highlighted (class plus a visible text cue, not colour alone); editing it to real content removes the highlight at once; removing the last list item adds it.
- [ ] The missing-information panel lists every question as received. A question with a field that exists on this ticket is a button that moves focus to that field's control; a question with `field: null` is plain text. Clicking a list field's question focuses its first item (or its Add button when the list is empty).
- [ ] The panel is unchanged by edits (it shows what the generator reported; it does not hide a question when its field is filled).
- [ ] The edited ticket is held in component state seeded from the response; a new response starts a fresh edit state.
- [ ] Vitest covers `isNotProvided`, the list functions, the field-path mapping, and the page behaviour above. `npm test`, `npm run lint` and `npm run build` pass.

## Questions for the human (answer before work starts)

1. **Blank text:** plan 4.8 highlights only the exact text `"Not provided"`. If the developer clears a field, should an empty or whitespace-only value also be highlighted as a gap? Proposal: yes, blank counts as not provided in the UI (the contract forbids empty strings in the output, so a blank is a gap too). The pure rule then is "trimmed value is empty or exactly `Not provided`".
2. **Blank list items:** Add creates an empty row for typing. Proposal: a list counts as not provided when it has no items or only blank items; blank rows are kept while editing and dropped when T4.2 reads the ticket out (rule 5 forbids empty list items). OK?
3. **Title length:** the validator limits generated titles to 120 characters. Proposal: no hard limit while editing, but a visible counter once past 120 ("Title is longer than 120 characters"), as a hint only; Jira itself allows 255. Or no counter at all?
4. **Questions after filling:** proposal above keeps every question visible even when its field is now filled (nothing to infer about whether the answer is good). Alternative: strike through a question whose field is no longer highlighted. Keep it simple (no strike-through)?
5. **State home:** proposal is local state in `TicketPage`, seeded from the response. T4.2 (preview) lives on the same page and needs no lift; T4.3 may lift it to `App` when the confirmation logic needs the "edited" flag. OK to defer?

## Log

### Plan

Human approved all five proposals (blank text and all-blank lists count as not provided; blank rows dropped by T4.2; soft title hint past 120; questions stay visible; state local to `TicketPage`). Tests first for the three pure modules, then the page. `fieldPaths.ts` lists the nine paths, which are text or list, per type, plus the control id. `listEditing.ts` has generic `addItem`, `removeItem`, `updateItem`, `moveItem` returning new arrays. `TicketPage` keeps `texts: Record<path, string>` and `lists: Record<path, {id, text}[]>` (stable row ids for keys), seeded from the response and reset when the response changes (key on the response in `App`-free way: `useState` initialiser plus a `key` set by the parent is outside the file list, so the page resets state in an effect-free way by deriving a seed key from the response object and remounting an inner component). Focus links use `document.getElementById`. No ⚠ VERIFY facts.

### Decisions

- Reset on a new response is done in `TicketPage` by comparing the stored `source` with the `response` prop during render (no effect, no parent `key`), so `App.tsx` is untouched.
- `isNotProvided` compares the trimmed text, so `" Not provided "` also counts; `"Not provided."` and other cases do not.
- Cue is the visible text "Needs content" plus a left border and tint, so the highlight is not colour alone.
- Layout moved from `dl/dt/dd` to `div.field` with a label; the page gets a plain `h1` "Review ticket" because the title is now an input. CSS for `dt`/`dd` removed (no other users).
- **File outside the list:** `web/src/App.test.tsx` had one assertion of the old read-only page (title heading, no textbox). I changed it to read the Title input's value; nothing weakened. Flagged for the human.
- Each missing-information entry no longer shows the field path in brackets; a question is a button when it names a field of this type, plain text otherwise.
