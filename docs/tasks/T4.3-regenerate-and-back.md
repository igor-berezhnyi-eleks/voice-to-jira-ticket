## Goal

Page 2 gets a **Regenerate** button that asks the API for a new ticket from the same transcript, and asks for confirmation first when the user has edited fields (the new ticket replaces the edits). **Back to transcript** returns to Page 1 with the transcript untouched.

## Where things stand (read from the code)

- `App.tsx` already holds the transcript, so Back already keeps it; Page 1 reads it from `App`. This is only pinned by a test, not built.
- There is **no Regenerate button** yet. Page 1 owns the `generateTicket` call, the running state and the error mapping (`describeGenerationError`).
- Page 2 edits live in `TicketPage` state, seeded from the response. A new `response` object resets them (this is what Regenerate will use). Back discarded them silently before this task.
- There is no "was it edited?" check yet.

## Acceptance criteria

- [ ] `hasEdits` is false for an untouched ticket, true after any text change, list row add/remove/move/edit, and false again when the user types the original text back. Whitespace-only differences and blank list rows that the read-out drops do not count as an edit (it compares what Copy would write, not raw state).
- [ ] Regenerate is visible on Page 2 next to Back. With no edits it sends the same transcript to the API at once, with no confirmation.
- [ ] With edits it asks first: "Regenerating replaces your edits with a new ticket. Continue?" with Replace and Cancel. Cancel changes nothing and sends no request; Replace sends the request.
- [ ] While the request runs the button is disabled and a "Generating…" status shows; the current ticket and edits stay on screen. On success the new ticket replaces the old one and the edit state is fresh. On failure the edits stay and the error is shown with the same messages as Page 1 (`describeGenerationError`), with the same Retry rule.
- [ ] Back returns to Page 1 with the transcript text exactly as it was; a running regenerate request is aborted on Back or on leaving the page.
- [ ] Back with edits asks first (human answer to question 3): "Going back discards your edits to this ticket. Continue?" with Discard and Cancel; Cancel stays on the page with the edits. With no edits, Back goes at once.
- [ ] `npm test`, `npm run lint` and `npm run build` pass.

## Questions for the human (answer before work starts)

1. **Where does the Regenerate request live?** Proposal: in `TicketPage` (it calls `generateTicket` itself and reports the result up), so Page 2 shows progress and errors in place and keeps the edits if it fails. Alternative: send the user back to Page 1 and auto-generate there (simpler, but loses the edits even on failure). Proposal OK?
2. **What counts as "edited"?** Proposal: the ticket as Copy would write it differs from the generated one (typing the original text back, or whitespace-only changes, are not edits). Alternative: any keystroke counts. OK?
3. **Back with edits:** Back currently throws the edits away silently, and the plan asks for a confirmation only on Regenerate. Proposal: keep that (no confirmation on Back), because Back lands on a page where the transcript is intact and Generate is one click. Alternative: confirm on Back too when there are edits. Which?
4. **Confirmation style:** an inline panel (text, Replace, Cancel) under the buttons rather than a browser `confirm()` dialog. OK?
5. **Wording** of the confirmation: "Regenerating replaces your edits with a new ticket. Continue?" with Replace / Cancel. OK, or do you prefer other words?

### Decisions

- `Draft.original` holds the seeded values read out through `editedTicket`; `hasEdits(original, current)` compares the two read-outs as JSON, so whitespace, blank rows and typed-back text are not edits.
- Retry and Regenerate share one handler, so Retry asks again when edits exist (edits made after a failure are never replaced unasked).
- `TicketPage` takes `transcript` and `onRegenerated` props; `App` passes the transcript and `setResult`. Back keeps the transcript (it already lives in `App`; a test pins it) and, by the human's clarified answer to question 3, asks for confirmation when there are edits (same panel, Discard / Cancel; one `confirming` state of `'regenerate' | 'back' | null`).
- The `llm_refused` message says "press Generate ticket", written for Page 1; on Page 2 it still reads correctly after Back. Not changed.
- Edits typed while a request runs are replaced when it succeeds (not blocked). Not changed.
- No new dependencies.
