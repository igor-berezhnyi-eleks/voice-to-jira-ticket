## Goal

The ticket contract exists once, as C# records, with a JSON schema exported from them, a committed schema snapshot that detects drift, and a validator that enforces the five rules of plan 4.3.

## Files

- `src/VoiceToTicket.Api/Features/Tickets/Contract/**` (records, `TicketType`, JSON serializer options, schema export)
- `src/VoiceToTicket.Api/Features/Tickets/TicketValidator.cs`
- `contract/ticket.schema.json` (written by the snapshot test only — the guard hook blocks direct edits)
- `tests/VoiceToTicket.Api.Tests/Tickets/**`

## Out of scope

- Endpoints, generators, the prompt, TypeScript types.

## Acceptance criteria

- [ ] Records match plan 4.3 exactly (names, nullability, list types). JSON is camelCase with enums as strings; round-trip test for a Bug and a Feature example.
- [ ] Schema is exported with `System.Text.Json.Schema.JsonSchemaExporter` and transformed so every object has `additionalProperties: false` and all properties are `required` (nullable ones allow `null`).
- [ ] Snapshot test: compares the exported schema with `contract/ticket.schema.json`; fails with a clear message on difference; rewrites the file only when `UPDATE_SNAPSHOTS=1` is set.
- [ ] `TicketValidator` returns a list of errors (empty = valid), one unit test per rule in 4.3 for both the passing and failing case (at least 10 tests), including: Bug with `feature` set; `"Not provided"` field without a missing-information entry; empty list without an entry; unknown `field` path; whitespace list item; title over 120 characters.
- [ ] The field paths accepted in `missingInformation.field` are defined in one place and used by the validator (later by the prompt and the UI).
- [ ] `dotnet build` 0 warnings; `dotnet test` passes.

### Decisions
- ⚠ VERIFY result (2026-11-05, https://platform.claude.com/docs/en/build-with-claude/structured-outputs.md and the `claude-api` skill): `additionalProperties: false` is required on every object; every property should be in `required` (limit: 24 optional parameters, we use 0); nullable values are union types through `anyOf` or type arrays such as `["string", "null"]` (limit: 16 per request, we use 3: `bug`, `feature`, `missingInformation.field`); `minLength`/`maxLength` are **not** supported, so the 120-character title limit stays in `TicketValidator` only. **Nullable objects are accepted, so the plan 4.3 fallback shape is not needed.** Not confirmed by a real API call (see Not verified).
- No new dependencies. `System.Text.Json` and its schema exporter are part of .NET 10.
- `TicketJson.Options` reads strictly: missing properties, nulls in non-nullable fields, unknown properties, wrong casing and numeric enums are `JsonException`s. This matches the schema and lets T3.2 map them to `llm_invalid_output`. Looser cases remain, all reachable only if the API breaks the schema: `JsonStringEnumConverter` accepts other casing (`"bug"`), surrounding spaces (`" Bug"`) and comma-separated values (`"Bug, Feature"` parses as `Feature`); null inside a list parses (`RespectNullableAnnotations` does not cover list elements); and a top-level JSON `null` deserializes to a null `Ticket`. **For T3.2: `TicketResponseParser` must map a null result to `llm_invalid_output` before calling the validator, which would otherwise throw.** `TicketValidator` reports null list items as errors (rule 5) rather than throwing, so they become `llm_invalid_output`. The enum cases are accepted: rejecting them needs a custom converter, which would lose the exporter's `enum` schema.
- Field paths (`TicketFields`): `title` and `description` are accepted as well as the section fields, because the reporter may be asked about them even though they cannot be `"Not provided"`, and rejecting that would turn a harmless question into `llm_invalid_output`. `type` is not accepted (plan 4.7 rule 2 uses `field: null` for that question). Plan 4.3 does not list the paths; the human confirmed this choice at the gate. A test checks the paths against the exported schema, so the two cannot drift.
- Rule 5 also applies to `missingInformation[].question` (the text of that list's items).
- Rule 3 applies only to the section of the ticket's type; a section of the wrong type is rule 1's error.
- Validator errors name fields and indexes and never quote values, because values come from the transcript and T3.2 may log the errors.
- `$ref` is not produced by the exporter for this contract; the keyword test fails if that ever changes.

### Human decisions at the contract gate (2026-11-05)
- Required fields: Bug = type, title, description. Feature = type, title, description, acceptance criteria.
- Meaning of "required", confirmed by the human: **a Feature with no described acceptance criteria keeps `[]` plus a missing-information question** (plan 4.3 unchanged; FEATURE-03 stays valid). Other detail fields stay on the ticket as `"Not provided"` or `[]` with a question. The schema and snapshot do not change.
- Rule 3 extended: a blank `bug.*` or `feature.*` string is an error even with a missing-information entry, because a gap is exactly `"Not provided"` (plan 4.7 rule 5). Previously `"environment": ""` passed and would have been neither highlighted nor asked about.
- Field paths confirmed by the human: `title` and `description` are accepted in `missingInformation.field` and `type` is not (a question about the type uses `field: null`).
- Rule 5 extended, human decision: `"Not provided"` as a list item or as question text is an error, even with a missing-information entry, because a list with no support is `[]` (plan 4.7 rule 5). Only an exact match counts; an item that merely mentions the words passes.
- Plan 4.3 is not edited; the extensions are recorded here and in the `docs/status.md` decision log.

### Notes for the study
- Harness: the snapshot guard kept the schema generated through its test, and the stop check stayed green. Neither could catch the gaps found here (blank strings, the marker inside lists); those came from the agent's reading of the plan and the reviewer's probing, and were settled by the human at the gate.
- The human's short statement about required fields looked like a contract change, but it conflicted with plan 4.3 and frozen scenario FEATURE-03 if read as "must be non-empty". The agent checked the scenarios and asked before changing anything; the confirmed meaning needed no schema change.
- The agent's first mutation check produced no result because the mutated record did not compile. The empty output was noticed and the check repeated with a compiling change; a green-looking "no failure line" would otherwise have counted as evidence.
- Writing the schema tests against an allow-list of keywords and walking schema positions only (the ticket has a property called `type`) avoided a false pass from a naive recursive search.
- The reviewer found what the agent's tests did not: `RespectNullableAnnotations` does not cover list elements, and comma-separated enum values parse. It found them by probing inputs in a scratch copy, not by reading the code. The agent's comment claimed more than the code guaranteed.
