# T5.2b — One retry on invalid model output

- **Milestone:** M5
- **Status:** done
- **Depends on:** T5.2 (runner and first evaluation run, done), T3.2 (Claude generator)
- **Plan sections:** 3 (D15), 4.4, 4.6, 6 (T3.2, T5.2), 7.2, 7.5
- **Parallel-safe with:** none; do it before T5.3 and T5.4, so every later run uses the final behaviour

## Goal

When Claude returns a ticket that cannot be used (`llm_invalid_output`), the generator tries once more before failing, and every result says how many attempts it took and whether the first one was valid, so the evaluation reports both first-attempt and with-retry compliance.

## Why

The first evaluation run (`eval/results/20261111-1244/`) gave 18 of 19 valid tickets for `claude-haiku-5-5` and 19 of 19 for `claude-sonnet-5-5`. The Haiku failure was BUG-04 run 1: `bug.stepsToReproduce[0]` was empty or "Not provided", which the prompt already forbids twice. One sample cannot show whether it is a flaky slip or a prompt defect. A retry is cheap on Haiku and spares the user an error that a second try would fix. Decision D15 banned retries because they hide the failure rate; this task keeps the rate visible instead of banning the retry.

## Out of scope

- Any prompt change (that is a tuning round and needs a full re-run).
- Retrying anything other than `llm_invalid_output`: refusals (`llm_refused`), truncation (`llm_truncated`), timeouts, 5xx and 429 stay as they are (the SDK already retries connection errors, 5xx and 429 by itself).
- A retry setting, backoff, or more than one retry.
- Changing the validator, the contract, the scenarios or the schema.
- Re-running the evaluation (the human decides when; see Verification).
- Feeding the failed output or its error back to the model in the retry (see proposal 2).

## Proposals (answer or say "all as proposed")

1. **What is retried.** Only `llm_invalid_output` (no text, unexpected stop reason, not a ticket in the expected format, or the validator rejects it). Exactly one retry, so at most two Claude calls per request. A fixed constant, not a setting.
2. **Same request again.** The retry sends the identical request. No error feedback to the model: feedback would include text derived from the transcript, complicate the prompt contract, and make a fix depend on a changed conversation. If you want feedback, say so and this becomes a larger task.
3. **What the result says.** `GenerationResult` gets `Attempts` (1 or 2) and `FirstAttemptValid` (bool). `DurationMs` covers both attempts; `Usage` sums both. The HTTP response gets the two fields too (extra fields are ignored by the web client; plan 4.4 is updated). Alternative: record them only in logs and the evaluation. Proposed: add to the result, because the runner needs them and a second code path for it would be worse.
4. **Failure after the retry.** If the second attempt is invalid too, the API answers with the second attempt's `llm_invalid_output` exactly as today. The runner records such a failure as 2 attempts, first attempt invalid. A non-retried failure (refusal, timeout) is 1 attempt; if the first attempt was invalid and the retry then hits a timeout or another error, that error is returned and the run records 2 attempts, first attempt invalid.
5. **Timeout.** The existing `TimeoutSeconds` (60) applies to each attempt separately, so a request can take up to about 120 s in the worst case. Alternative: one deadline for both, which can leave the retry too little time. Proposed: per attempt.
6. **Plan wording.** D15 becomes: "One automatic retry on a semantically invalid ticket; the result records the attempts and whether the first was valid, and the evaluation reports both rates." Plan 7.2 (contract compliance) and 7.5 are read as: the Go threshold applies to first-attempt compliance, and with-retry compliance is reported next to it. The report states which one decides the verdict. Proposed: first-attempt decides; with-retry is an extra column and a stated condition.
7. **Fake generator.** Always 1 attempt, first attempt valid. No way to force a retry through the API in Docker or the demo; the retry is tested with a fake `IClaudeMessages`.
8. **Existing results.** The committed run `20261111-1244` has no attempt fields. It stays as it is (it was a single-attempt run by definition); T5.4 treats missing fields as 1 attempt. No re-run is required by this task. A new run is the human's call, costs about 38 calls, and counts as part of the report only if the prompt hash is unchanged.

## Acceptance criteria

- [ ] An invalid first reply followed by a valid one returns the ticket with `Attempts` 2 and `FirstAttemptValid` false; the request was sent twice, identically.
- [ ] A valid first reply makes one call and returns `Attempts` 1 and `FirstAttemptValid` true.
- [ ] Two invalid replies in a row throw `llm_invalid_output` (502) once, after exactly two calls.
- [ ] A refusal, truncation, timeout or SDK error on the first attempt is not retried (one call, same error code as before).
- [ ] An error on the retry itself is mapped as it is today (timeout 504, unavailable 503) and not turned into `llm_invalid_output`.
- [ ] `DurationMs` and token usage cover both attempts when a retry happened.
- [ ] Cancellation by the caller during or between attempts stops without a retry.
- [ ] The log never contains transcript or model text; a retry logs only a warning with the attempt number and the error code.
- [ ] The evaluation runner records `attempts` and `firstAttemptValid` per run, for failures too; `<model>.json` carries them; the scoring sheet shows attempts for a run that needed a retry; a summary per model reports first-attempt validity and with-retry validity counts.
- [ ] The fake run in the default `dotnet test` still produces well-formed output.
- [ ] `docs/implementation-plan.md` D15, 4.4 and 4.6 match the new behaviour, and the decision is in the status decision log.
- [ ] The default `dotnet test` stays offline and green; the API still starts with the Fake provider and no key.

### Decisions
- Generator: a loop of at most two attempts (`MaxRetries = 1`); each call has its own linked deadline (`CallAsync`). Only an `ApiException` with `llm_invalid_output` on attempt 1 retries; the same `ClaudeRequest` is sent. Usage is summed; `DurationMs` is measured from the first call to the end.
- Beyond the proposals' wording but needed for proposal 4: a failure thrown by `GenerateAsync` carries the number of model calls in `Exception.Data["VoiceToTicket.Attempts"]` (`ClaudeTicketGenerator.AttemptsDataKey`), so the runner records 2 attempts when the retry itself failed (timeout, unavailable, second invalid). A failed run is always `firstAttemptValid: false`. A generator that sets no tag counts as 1 attempt.
- `GenerationResult` has the new fields without defaults, so no caller can forget them. Both appear in the HTTP response (`attempts`, `firstAttemptValid`). `GenerateTicketEndpointTests.Response_has_exactly_the_planned_shape` was updated for them (inside the file list).
- Runner: `RunRecord` gets `Attempts` and `FirstAttemptValid`; `ModelResult` gets `Totals` (`Runs`, `FirstAttemptValid`, `Valid`), written to the JSON and the scoring sheet header ("valid on the first attempt … valid after the retry"). A run that needed a retry is marked `**Attempts: 2**` in the sheet.
- `web/src/api.ts` not changed: the client ignores unknown response fields and does not use the new ones.
- Plan edited by agreement: D15, 4.4 (response), 4.6 (`GenerationResult`, retry bullet), 7.2 (contract compliance reported twice).
