## Goal

The API can connect a user to Jira Cloud. `POST /api/jira/session` checks an email and API token against `GET /rest/api/2/myself` and stores them in an encrypted cookie. `DELETE` removes the cookie, and `GET /api/jira/status` reports whether Jira is enabled and connected. Every Jira error maps to a `jira_*` code.

## Acceptance criteria

- [ ] `JiraOptions` uses `ValidateOnStart`, with all keys from plan section 5 and their defaults. With `Enabled=true`, start fails without an absolute https `BaseUrl`. The other keys are optional suggestions. A configured `PreferredIssueTypes` list **replaces** the default list (it does not append), and an empty configured list means "no preference". Both are tested through real configuration binding. With `Enabled=false`, nothing about Jira is validated and the app starts as before.
- [ ] `JiraClient` is a typed `IHttpClientFactory` client. It sends `Authorization: Basic base64(email:token)` and `Accept: application/json`, applies `Jira:TimeoutSeconds`, and passes the `CancellationToken` everywhere.
- [ ] Jira statuses map as in plan section 6. 401 → `jira_auth_required` (on `/session`: `jira_auth_denied`), 403 → `jira_forbidden`, 404 → `jira_not_found`, 400 or 422 → `jira_rejected` (with `errors` and `errorMessages`), 429 → `jira_rate_limited` with `retryAfterSeconds` when the header is present, 5xx or network → `jira_unavailable`, timeout → `jira_timeout`. Each case has a stub-handler test.
- [ ] `POST /api/jira/session` returns `{displayName}` and sets a cookie that is HttpOnly, SameSite=Strict, `Path=/api/jira`, Secure when HTTPS, and encrypted with Data Protection. Tests show the cookie value contains neither the token nor the email in clear text.
- [ ] A cookie older than `Jira:SessionHours` (fake `TimeProvider`) is treated as absent, and a tampered cookie is treated as absent.
- [ ] A Jira 401 on any call made with the session clears the cookie in the response.
- [ ] `DELETE /api/jira/session` returns 204 and clears the cookie. `GET /api/jira/status` returns `{enabled, connected, displayName?, defaultProjectKey?}` without calling Jira.
- [ ] With `Enabled=false`, `/session` returns 404 `jira_not_configured`, and `status` returns `enabled: false`.
- [ ] `POST /session` with a non-JSON body returns 415.
- [ ] A capturing-logger test shows that no log entry contains the token, the email or the `Authorization` header.
- [ ] `contract/jira.schema.json` has a snapshot test like `TicketSchemaTests`, and `npm run gen:contract` writes `web/src/jiraContract.ts`. Both are protected by the hook.
- [ ] A spike in this task confirms that `json2ts` turns a discriminated union (the `FieldValue` shape from plan 4.3) into a TypeScript union without `any`. The result is recorded in the log. If it can't, propose another C# shape before J2.
- [ ] `docker compose config` shows the `dp-keys` volume mounted and `DataProtection__KeysPath` set.
- [ ] Default `dotnet test` passes offline, and `node scripts/check.mjs` passes.

Manual check for the human (needs your token, entered by you):

- Run the API in Development and call `POST http://localhost:5080/api/jira/session` with your email and token (for example from the Swagger UI). Expect your display name, then `GET /api/jira/status` → `connected: true`. With a wrong token, expect 401 `jira_auth_denied`.
