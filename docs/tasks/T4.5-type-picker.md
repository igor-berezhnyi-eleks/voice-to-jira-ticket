## Goal

On the ticket page the reporter can change the ticket's type (Bug / Feature) from a dropdown when the model guessed wrong or the report was ambiguous. The ticket is converted in the browser at once, and a "Regenerate as <type>" button asks Claude for a proper ticket of the chosen type.

## Why

Plan 4.3 rule 2 makes the model pick "the more likely type" for an ambiguous report and add a question (`field: null`), and plan 4.8 says the type cannot be switched client-side ("edit the transcript and regenerate"). The human decided (2026-11-11) that this is too awkward: the dropdown is always visible, conversion is instant, and a regenerate is offered for a better result.

## Proposals (answer or say "all as proposed")

1. **Dropdown.** A native `<select>` labelled "Type" in the Page 2 header replaces the read-only badge. Options Bug and Feature, current type selected. Keyboard and screen-reader friendly by default.
2. **Instant conversion, client-side, nothing lost.** A pure function `convertTicket(edited, toType)` works on the edited read-out and never calls the API. Title and description are kept.
   - Bug → Feature: `proposedBehavior` ← `expectedResult`; `userNeed` and `acceptanceCriteria` start as "Not provided" and `[]`. Steps, actual result and environment, where provided, are appended to the description as short labelled lines so nothing the user typed is thrown away.
   - Feature → Bug: `expectedResult` ← `proposedBehavior`; steps `[]`, actual result and environment "Not provided". User need and acceptance criteria, where provided, are appended to the description.
   - Missing-information questions: those whose `field` belongs to the other type are dropped; `field: null`, `title` and `description` questions stay (including the "which type?" question). The existing "Needs content" highlight shows the new gaps.
3. **Regenerate as the chosen type.** After a conversion the page shows a notice: "Converted from Bug in your browser. Regenerate as Feature for a better ticket." with a "Regenerate as Feature" button. It posts `{ transcript, type }` to `POST /api/tickets` (new optional `type`: `"Bug"` or `"Feature"`; anything else is 400 `validation`). It uses the existing Regenerate flow, including the confirmation when there are edits, error messages and Retry.
   - **Prompt:** `TicketPrompt.System` stays byte-for-byte as it is. Only `UserMessage(transcript, type)` changes: when a type is given, a line before the `<transcript>` block says: "The reporter has decided this is a {Bug|Feature}. Write a {Bug|Feature} ticket whatever the report sounds like, and do not ask which type it is." The type is an enum, so no free text enters the message. With no type, the message is identical to today's. Consequence: the committed evaluation results and the prompt hash stay valid, and this is **not** a prompt tuning round.
   - **Check:** if the ticket that comes back has a different type from the one requested, the generator treats it as an unusable ticket (`llm_invalid_output`) and the existing single retry applies.
4. **Interface.** `ITicketGenerator.GenerateAsync(string transcript, CancellationToken cancellationToken, TicketType? requestedType = null)`, a default parameter so every existing caller and test stays as it is. The Fake honours `requestedType` (forces that type, otherwise as today). The response body is unchanged.
5. **Switching back.** The page keeps the last edited state of each type it has shown, so choosing the original type again restores the user's earlier edits and the generated ticket, and the "Converted" notice goes away. Choosing a type the page has not shown converts from the current edited ticket. Regenerate (with or without a type) and Back reset this state as they do today. Alternative: no memory, every switch converts from the current ticket (simpler, but a switch and switch-back drops the original type's own fields). Proposed: memory.
6. **Confirmations.** Converting in the browser never asks for confirmation (it is reversible by proposal 5). "Regenerate as <type>" asks as Regenerate does today when there are edits.
7. **No scored evaluation.** The forced-type path changes only the user message, and its inputs are the same scenarios. I propose one small, optional real spot check after building: AMBIGUOUS-01 and MIXED-01 each forced to Feature on Haiku (about 2 calls), checked by eye for type, no leftover "which type?" question, and no invention. Not part of the report's numbers. Needs your OK to run.
8. **Page header text.** The existing header shows model and generation time; after a conversion the model and time still describe the generated ticket, and the notice says the fields were converted. The preview, Copy and Save as JSON use the converted ticket (`ticket-<type>-…json` with the new type).
9. **E2E.** One extra step in the existing Playwright smoke test: switch a Bug to Feature with the Fake provider, see the notice, and see the Feature fields. `npm run e2e` stays a manual step for the human (not part of `check.mjs`).

## Acceptance criteria

- [ ] Page 2 shows a Type dropdown with Bug and Feature, the current type selected, at all times, for every ticket.
- [ ] Choosing the other type shows that type's fields at once with no network request, keeps title and description, and shows the "Converted" notice with a "Regenerate as <type>" button.
- [ ] `convertTicket` is pure and unit-tested for both directions: mapped fields, text moved into the description only when provided, questions of the other type dropped, `field: null`/title/description questions kept, blank rows and `Not provided` handled as in `editedTicket`.
- [ ] The converted ticket validates as a ticket of its type when read out through `editedTicket` (the output has the shape `TicketValidator` expects: details of exactly one type; "Not provided" for empty strings).
- [ ] Switching back to a type already shown restores its edits and removes the notice (proposal 5).
- [ ] Preview (Plain and Jira wiki), Copy and Save as JSON follow the selected type.
- [ ] "Regenerate as <type>" sends `{ transcript, type }`; the response replaces the page's ticket as in Regenerate, with its confirmation, error messages and Retry; on failure the converted ticket and edits stay.
- [ ] `POST /api/tickets` accepts an optional `type` of `Bug` or `Feature`, rejects any other value with 400 `validation`, and behaves exactly as before without it.
- [ ] With a type given, `TicketPrompt.UserMessage` contains the type sentence before the transcript block; without it, its output is identical to today's (pinned by a test), and `TicketPrompt.System` is unchanged (pinned by a hash or equality test against the current text).
- [ ] The Claude generator treats a returned ticket of the wrong type as `llm_invalid_output` and retries once; the type is part of the retried request.
- [ ] The Fake provider returns the requested type.
- [ ] No change to the contract, schema or `web/src/contract.ts`; no new dependencies.
- [ ] The default `dotnet test` and `npm test` stay offline and green; lint and build are clean.
