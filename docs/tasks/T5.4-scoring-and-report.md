## Proposals (answer or say "all as proposed")

1. **Which run is scored.** Only `20261111-1429`: it has the script path and the audio path, both models, the retry, and the final prompt hash. `20261111-1244` and `20261111-1303` are mentioned in the report as earlier runs (the Haiku contract failure that led to D15) and are not scored. The older sheets get no human scoring. Alternative: also score `1244` to show before/after the retry (adds 38 tickets; not needed, since the retry is not a prompt change).
2. **How much to score.** All 58 tickets (19 script + 10 audio per model) are the plan's intent. To make it bearable, the three repeated scenarios (AMBIGUOUS-01, NOISY-01, MIXED-01) have 4 script tickets each: proposed that you score **run 1 fully** and, for runs 2–4, only the invention and usability fields (facts and missing flags are stable only if type and content are; if a repeat differs, score it fully). Alternative: score everything fully (more work, same conclusions in most cases).
3. **Time-saved test (7.4).** You write 3 tickets by hand in Jira's format and dictate + review 3 comparable ones (use the real app with Claude, Sonnet). Time each from first keystroke / button to a ticket you would paste into Jira. Record in `time-test.md` as a small table: item, hand minutes, voice minutes (recording + generation + edits), what the item was (by scenario ID if you reuse a script; the recordings you already made are fine). Proposed: reuse three scenarios (a Bug, a Feature, and BUG-04 or another low-detail one) as the content so the comparison is fair. The agent computes the percentage; with n = 3 it is stated as indicative only.
4. **Summary script.** `scripts/score-summary.mjs` (Node, no dependencies) parses the filled `scoring-sheet.md` plus `<model>.json` and `stt.json` and prints, per model and per path (script / audio): contract compliance (first attempt and after retry), type accuracy on the 7 clear scenarios, fact coverage, missing-info recall, spurious missing items, invention counts (minor / critical), usability shares, trap hits, latency and tokens, and the threshold band for each row. It is needed to avoid hand-counting 58 tickets and makes the report reproducible. Not a build script; run manually and by the report author. Alternative: count by hand inside the report (error-prone). Needs your yes since CLAUDE.md says not to invent scripts.
5. **Which numbers decide.** The Go thresholds use the **script path** (plan 7.5 is written for the ticket quality; the audio path adds STT effects). The audio path is reported next to it as "voice in" with its own table and the differences (type changes, lost facts, WER). If the audio path would fall into a worse band than the script path, the verdict is Conditional Go with that as the condition rather than a lower verdict, unless invention/type/usability alone would be worse. Alternative: the verdict is the worse of both paths.
6. **Report shape.** `docs/evaluation-report.md`: summary and verdict per model with a model recommendation (first); method and what was run (runs, hashes, commit, tuning rounds = 0, scenarios version `eval-scenarios-v1`, scoring rules); results table per model against the thresholds; STT section (WER per scenario, effect on tickets); the time test; 3–5 before/after examples (transcript → ticket, picked to show a good case, a typical edit, and a failure; scenario scripts are made-up so they can be quoted); failure analysis (every critical or minor invention, every type miss, every Haiku contract failure, with cause guess); cost per ticket from the token counts; known limits (10 scenarios, one scorer, same scorer wrote the scenarios or not, PoC statistical weakness, numbers moving 10 points per scenario); conditions for a Conditional Go and next steps. No marketing tone; failures are stated.
7. **Cost per ticket.** Computed from the recorded input/output tokens and the public price per model, which the agent looks up (⚠ VERIFY: model prices from current Anthropic docs, not from memory; record the source and date). If a price cannot be verified, the report shows tokens only.
8. **Sign-off.** The gate "Recommendation signed off" is passed only by your explicit yes after reading the report. Corrections after your reading are made and shown before the gate is set to done.
