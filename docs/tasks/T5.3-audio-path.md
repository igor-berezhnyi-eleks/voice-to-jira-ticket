## Goal

When recordings exist in `eval/audio/<id>.webm` and the STT container is reachable, the evaluation also transcribes each recording, computes the word error rate (WER) against the scenario script, and generates a ticket from the STT transcript, so the report can compare "script in, ticket out" with "voice in, ticket out".

## Proposals (answer or say "all as proposed")

1. **Opt-in switch.** The audio path runs only with `VTT_EVAL_AUDIO=1`, on top of `VTT_RUN_EVALUATION=1`. Without it the evaluation behaves exactly as today. Alternative: always run it when the files exist (which doubles cost without being asked). Proposed: the switch. If the switch is set and the STT is unreachable, the test fails with a clear message instead of silently skipping. A missing file for a selected scenario is reported as "no recording" and skipped; the others still run.
2. **What the audio path runs.** Per scenario with a recording: transcribe once (the STT is local and free, and does not depend on the Claude model), then generate once per model from the transcript. No repeats on this path (the three repeated scenarios stay repeated on the script path only). Cost for the audio path: 10 calls per model, 20 for both, on top of the script path's 38 when run together. Alternative: also repeat. Proposed: no.
3. **How the STT is called.** `SpeachesClient` is used directly (same code, same options and defaults as the API), built in the test with `IHttpClientFactory` from a small service collection (CLAUDE.md: never `new HttpClient()`). `Stt` settings come from the API's `appsettings.json` and `appsettings.Development.json` (so `http://localhost:8000`), overridable with environment variables (`Stt__BaseUrl`). Content type `audio/webm`. No retry (D2).
4. **WER definition.** Word-level edit distance (substitutions + deletions + insertions) divided by the number of reference words, case-insensitive. Normalisation before comparing: lowercase, punctuation removed (apostrophes inside words and dots between digits kept, so `3.8` stays one word), whitespace split. No number-word conversion and no hyphen rules beyond that, so "three" vs "3" counts as an error; this is stated in the report. The reference is the **script as written**. If the human deviated from the script while reading it aloud, those deviations count as STT errors; the report says so. Per scenario the result holds WER, reference word count and the three error counts; the run also reports the mean WER (words pooled over scenarios, not an average of ratios).
5. **Where the results go.** The same run directory. The STT transcripts and WER go in one new file, `stt.json` (STT model, language, and per scenario: transcript, WER, counts, STT time in ms). The per-model `<model>.json` gets an `audioRecords` list with the generation record for each recorded scenario (same record shape as today, plus the scenario id) so T5.4 can score both paths in the same way. Existing fields and the committed older runs stay valid (missing `audioRecords` means no audio path).
6. **Scoring sheet.** For each scenario with an audio ticket, the sheet adds a block "From audio" below the script-path tickets: the STT transcript (so the human can see the errors), the WER, then the ticket and the same empty scoring fields. The human scores these tickets too, so T5.4 can report the effect of STT errors. This adds about 10 tickets per model to score (Alternative: score only the automatic checks for the audio path. Proposed: score them, since the question the PoC asks is whether voice works, not whether text works).
7. **Privacy and logs.** STT transcripts are stored in the results (they are readings of the made-up scenario scripts, not real data) but never logged at Information or above, and the audio files themselves are never copied or committed. The plan's T5.3 text ("the human records … Download recording") is updated to say the files are the human's recordings and the audio path is opt-in.
8. **Automatic checks on the audio path.** Same as the script path: type match, validator result, trap hits, latency, tokens, attempts. The type match of the audio ticket is reported next to the script ticket's, so T5.4 can see a type that changed because of the STT. No "pass/fail" on WER.

## Notes

- The STT output is lowercase without punctuation at times (T2.1), so the normalisation matters; the unit tests pin it.
- `Transcription.DurationMs` is the API-side time of the call, not the audio length. Latency is therefore the STT time per recording; per-minute figures need the audio length and are out of scope.
- CPU transcription of a 60 s recording takes about 20 s (T2.1: 3.5 s per 10 s of audio), so the full audio path for ten recordings takes a few minutes. Set `Stt:TimeoutSeconds` high enough for NOISY-01 (largest file).
- Check the STT result format against `SpeachesClient` before using it: it reads `text` from a JSON response and trims it.
- Prompt hash stays unchanged, so the tuning-round count stays 0; this is not a tuning round.

### Decisions
- `Wer` (new, in the Evaluation project): DP edit distance with a stable back-walk for the substitution/deletion/insertion split. Words: letters and digits, lowercased; an apostrophe between letters and a dot between digits stay inside the word; curly apostrophes become straight. `WerResult.Rate` is null for an empty reference. `Wer.Pooled` is all errors over all reference words.
- `AudioTranscriber` calls `ISpeechToText` with `audio/webm` and the file name. A missing file is `Recorded: false`; a transcript with no words (the STT answers "." for silence) gets the code `empty_transcript` and no generation call, but its WER (1.0) is still kept. An `ApiException` from the STT is recorded with its code and the run continues.
- `SttResult.Unreachable` (something attempted, every attempt `stt_unavailable`) makes the entry test fail before any Claude call, naming `Stt:BaseUrl`. The entry test also fails when the switch is set and no selected scenario has a recording.
- `EvaluationRunner.RunAsync` takes an optional `SttResult`; audio tickets go to `ModelResult.AudioRecords` (omitted from JSON when null) and are not in `Totals`, so the script-path totals mean what they meant. `RunOnceAsync` now takes the transcript text.
- Scoring sheet: a "from audio" block per recorded scenario (transcript, WER, script-path type, ticket, empty scoring fields); a failed transcription block has no scoring fields. `ResultWriter.Write` and `ScoringSheet` take an optional `SttResult`.
- The entry test builds `SpeachesClient` through `AddHttpClient` from the API's `appsettings.json` and `appsettings.Development.json` plus environment variables. `RepoPaths` gained `Audio` and `ApiProject`.
- Plan T5.3 text updated by agreement (proposal 7). No new package; `Microsoft.Extensions.Http` came through the framework reference.
